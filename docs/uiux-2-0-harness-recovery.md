# Pause, cancel, resume, and the morning after (UIUX-P3-05)

> Generated by `scripts/uiux_harness_recovery_inventory.py`. Do not edit by hand: change the pane and regenerate.

A stopped run is a state with a cause, a checkpoint and a way forward, and it is drawn from the record the server already keeps: GET …/state and GET …/task. The four routes that answer it - pause, cancel, resume and abort - are pressable from the pane, and a refusal is a disabled button carrying the reason the runtime would give.

## What the pane could not do

`POST …/pause`, `…/cancel`, `…/resume` and `…/contain` were built for the moment a run stops, and the pane reached none of them. It had one control, Abort, which ends the pane's view rather than the work. A paused run was a mono line, a cancelled run was a mono line, a prepared resume was a mono line, and a worker that died left the task saying `running` with nothing said about it at all.

## The surface

`#harnessRecoveryPanel` sits under the session strip and above the durable log. It is one presentation - so it cannot be drawn without a cause and a `Kept:` line - over a facts list and a live note:

```
⚠ Paused at a safe boundary
  Cause: it stopped between steps: the operator asked the run to stop at the next safe
         boundary (operator_pause_requested). Nothing will move until something asks it to.
  Kept:  step 3 (seq 1, interrupted) is where a resume restarts, and the log above holds
         every step taken before it.
  [Resume from the checkpoint] [Cancel this task]
  Task              paused · epoch 0 · updated 07:12 AM
  Latest checkpoint seq 1 · step 3 · interrupted · 07:12 AM
  Recovery budget   0/3 retries · 0/3 replans · 0/3 rollbacks
  Task budget       0/25 steps · 0/3 recoveries
  Containment       0 in flight · 0 barrier(s) · 0 fenced origin(s)
```

Two routes feed it, both older than this story: `GET …/state` for the task status, the transitions and the checkpoints, and `GET …/task` for the recovery memory, the containment store and the budget. A field the record does not have is drawn as missing (`none recorded — nothing here can be resumed`), never guessed.

## The states

| State | What the surface says |
|---|---|
| `running`, this pane owns it | a pause lands at the next safe boundary; nothing is interrupted mid-action |
| `running`, this pane does not own it | the record cannot tell a run in another tab from a worker that died, and neither can the pane |
| `paused` | the transition's own reason, the checkpoint a resume restarts from, and the two presses that exist |
| `failed` | the failure as the runtime recorded it, and that a resume needs changed evidence |
| `blocked` | the unresolved effect by id, resume refused, and a cancel that turns it into a barrier |
| `cancelled` | what was fenced and revoked, and that no resume exists - a new session is the way forward |
| resume accepted | prepared at step N, `nothing has run yet`, and a control that continues it |
| nothing to recover | no surface at all |

## The actions

| Action | Route | What it costs |
|---|---|---|
| Pause at a safe boundary | `POST …/pause` | a deferred pause says it is deferred; pending approvals are rejected |
| Resume from the checkpoint | `POST …/resume` | one recovery slot, and a 409 if the record says no |
| Continue the run from step N | `/api/harness/run` with `resume: true` | only after an accepted resume |
| Cancel this task | `POST …/cancel` | fences the lease, revokes grants, contains processes; irreversible |
| Abort the run and stop following | `POST /api/harness/abort/{session_id}` | the view only; the record and the task are untouched |
| Start a new session | none | the only way forward from a cancelled task |

Cancel takes two presses, and any other action disarms it: a confirmation that outlives the reader's attention is a one-press cancel wearing a two-press label.

## A refusal is a state, not a surprise

Every reason the runtime would reject a resume is computed from the same record and stated before the press - the task state, a failed integrity check, unresolved consequential actions, a persisted barrier, a pending cancellation, an exhausted budget, a quarantine, unreadable recovery memory. The action stays visible and disabled, with the reason as its accessible description and the same reason in text:

```
Not available here — Resume from the checkpoint: the task is blocked on effects the
runtime cannot account for; 1 persisted barrier(s) hold this workspace, so it cannot be
taken exclusively; 1 consequential action(s) were left unresolved (act-seed-…): they must
be reconciled first.
```

When a press does reach the server and comes back refused, the pane prints the answer it got - the string `detail` a rejected transition carries, or the `{code, message}` a rejected handoff carries - instead of reverting silently.

## The events, where they happened

`turn/paused`, `turn/cancelled` and `turn/resume_prepared` were three one-line renderers that stated a reason and nothing else. They are one card now, saying what the event did (`0 in-flight process(es) were contained`, `2 consequential action(s) were left unresolved …`) and linking back to the surface that keeps saying it after the log scrolls past.

## The continuation the pane could not send

`/api/harness/run` accepts `resume`, and the pane never sent it - so a resume that had been accepted by the runtime was followed by a turn that started over from step 1. The request now carries the flag when a resume is prepared, and consumes the preparation in the same request.

## What this story had to preserve

| Preserved rule | Where it still lives |
|---|---|
| a pause defers to a safe boundary and says which it is | `api_pause_harness_session` |
| a cancel fences the lease, revokes grants, contains processes and reports what stayed unresolved | `api_cancel_harness_session` |
| a resume validates the checkpoint, the unresolved effects and the budget before preparing | `api_resume_harness_session` |
| containment quarantines and raises the holds a resume reads | `api_contain_harness_session` |
| `/task` still publishes the recovery memory and the containment summary | `api_get_harness_task_state` |
| `/state` still publishes the task status and the transition log | `api_get_harness_session_state` |

No endpoint was added: the surface posts only to pause, cancel, resume and the abort that already existed, and the inventory fails if a recovery route appears that the server does not mount.

## Checks and limits

`--check` re-derives 44 checks from the source - the markup, the 6 actions, the 11 refusals, the three event cards and the 7 server contracts - and fails on any of them. `node scripts/harness_recovery_walk.mjs` presses the same controls in a real browser against `scripts/harness_recovery_seed.py`, which drives the state machine into four stopped states and then answers with the real routes; it photographs seven states in [`media/harness-recovery/`](media/harness-recovery/README.md).

- the surface draws the record; it cannot tell a live worker from a dead one, and it says so instead of guessing. The product's own `recover_incomplete_transitions()` settles that question at startup, and the surface draws its answer (`recovered_incomplete_transition`).
- a resume prepares a run and consumes a recovery slot; it starts nothing. The pane says `nothing has run yet` and only the next `/run` continues the checkpoint.
- `Contain` has no control in this pane: it is an incident response that quarantines a session and revokes its grants, and an operator-facing button for it would be a one-press quarantine. Its effect is drawn - the holds it raises block a resume, and the surface says so.
- the pending-approval case is P3-03's surface: a pause rejects pending approvals, and the panel states that rather than redrawing the approval cards.
- the demo has no model runtime, so the walk cannot press Continue without a provider; the request the pane would send is read instead, and the walk says it did that.
