# Chat: the context a reply was given, and what its tools did

Generated by `python3 scripts/uiux_chat_context_inventory.py` — **never hand-edit this page**.

Every Chat answer records the context it was sent - persona, reasoning mode, tools, skills, message count and the directory that will be read - and prints it; every tool call prints a status word, its step, its time and the size of its arguments, with the arguments and the server's capped output one disclosure below; and a streaming turn reports how long it has been going and when the first token arrived, measured.

## The context line

| Field | What it is |
|---|---|
| `model` | the model the request was sent to, which is not always the one that answers |
| `persona` | the selected persona's label, not its prompt |
| `reasoning` | the reasoning mode the request carried |
| `tools` | tools on or off |
| `workspace` | the directory the pane literally sent - possibly nothing |
| `workspace_effective` | what the server will read instead when nothing was sent |
| `skills` | how many active skills went with it, printed only when there were any |
| `messages` | how many messages the request carried, system prompt included |

`chatContextSnapshot()` is called once, when the request is built, and the snapshot is stored on the turn: recomputing it at render time would describe the composer as it is now, not the request that was sent. The line is printed above the reasoning and the tools, with the whole sentence in its `title`. It opens with
the model because the turn header names the model that answered: if the server ever falls back, the header
and the context disagree, and a copied line names what was actually asked for.

The two workspace fields exist because they are two different facts. `workspace` is what the pane sent - often nothing, because the field is empty. `workspace_effective` is what `POST /api/chat/stream` will read in that case, `WORKSPACE_ROOT`. Printing only the second would hide what was sent; printing only the first would leave the reader guessing.

## Tool calls

A call used to be a border colour: cyan-ish for a success, red-ish for a failure, and a JSON blob cut off at 72 characters. Now each row is:

- a **status word** - `OK` or `FAILED` - with a tone, so colour is reinforcement rather than the message;
- the tool name, its `step`, its elapsed time, and the byte length of its arguments;
- a disclosure holding the **whole argument object** and the server's output, labelled with the cap the server applies (500 characters in `app.py`).

Above the rows, one line counts them: `2 tool calls · 1 failed · 412 ms`. A reader who does not open a single disclosure still knows whether the answer used tools, and whether any of them failed.

The pane reads exactly the fields the route yields on a `chat_tool` event - `step`, `tool`, `args`, `ok`, `elapsed_ms`, `preview` - and the inventory fails if either side changes.

## While it streams

A turn in flight says `streaming… · 3.2s · first token 0.41s · 128 chars`, and the finished turn keeps the elapsed and first-token figures beside the model's own tok/s and token count.

Both numbers are taken with `performance.now()`: the request records when it went out, and the first token records itself when the pane applies it. Before a token arrives the turn says *waiting for the first token* rather than showing a zero. The clock is a snapshot per render - the pane has no timer - so it stops when the stream does, which is the honest behaviour for a figure nobody is measuring. A finished turn freezes its
elapsed time when the stream ends (`endedAt`), so a later re-render cannot keep counting seconds; and
`aria-busy` on the transcript follows a turn that has no usage yet, not only the pane's own send flag, so a
turn arriving from a resumed stream is not announced as idle.

## Checks and limits

- the streaming clock is a snapshot taken at each render: the pane has no timer, so the number stops moving when no token arrives. That is deliberate - a frozen clock is a fact, a guessed tick is not - and it is stated here and on the page.
- the tool output is whatever the server sent, capped at 500 characters in app.py; the pane says so instead of implying the model saw more.
- the first-token time is when the browser applied the first token it received, which includes the network and the pane's own render cost - it is not the model's TTFT, and the perf record in the rail is where the model's own number lives.
- the walk writes the turns it judges, because a scripted demo reply does not call tools; the real send it also performs proves the context line on a live request.

`node scripts/chat_context_walk.mjs` writes a turn with a passing and a failing tool call and holds the pane against it: statuses, counts, full arguments, the context line; then it sends a real message and checks the context recorded on that turn against the composer it was sent from.

## Regenerating

1. Change the pane in `static/index.html`, or a field in the `chat_tool` event.
2. `python3 scripts/uiux_chat_context_inventory.py`.
3. `node scripts/chat_context_walk.mjs` against a running `scripts/demo_tour.py --serve`.
