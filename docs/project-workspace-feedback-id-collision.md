# Feedback capture identity collision

In a disposable application database, two different sessions submitted the same caller-supplied feedback ID. Before this change both capture requests returned 200: the second globally keyed upsert replaced the first record, and the original session could no longer list it. This was reproduced through the integrated routes, not just the storage class. The caller was already permitted to call those routes; this observation does not establish an authentication bypass.

Capture now uses an atomic SQLite insert with a uniqueness conflict refusal. A duplicate ID returns HTTP 409 without writing a feedback record or appending a capture event. The ID cannot be reused even after withdrawal; the retained record remains visible in its original session. The confirm, withdraw and promotion rules are not changed. Clients that intentionally supplied an existing ID to overwrite it must instead use a new ID; this is a deliberate compatibility change. Generated IDs already use random UUIDs, but the same collision refusal applies to them.

The focused route regression checks collisions in the same and a different session against an already confirmed record, then checks the withdrawn record cannot be resurrected into the other session. A simultaneous two-writer store regression requires exactly one insertion and one conflict. Reverting the capture route to upsert, replacing conflict refusal with an overwrite or a silent success, changing the 409 response, and appending a capture event before the refusal were each caught. The restored focused suite passed 59 tests. A broader feedback, reference, recovery and required-browser run passed 115 tests with two optional DOM probes skipped; those probes ran in a separate reference and recovery run with the dependency present, passing all 52 tests.

Refreshed accessibility and performance evidence passed 120/120 and 21/21; the cross-tab walk passed 2,200/2,200 checks over 48 captures. Backend safety passed 309 tests and 16 isolation checks, with isolation unqualified and blocked. The historical release gate passed 37/37 artifact checks and 7/7 phase gates; its old preservation approval remains unbound. These checks are not release approval.

## Cross-session promotion collision containment

A subsequent integrated-route reproduction showed that promotion could overwrite a different session's record when its derived preference ID collided with an existing ID. The storage upsert now atomically refuses to transfer an existing feedback ID to another session; promotion returns HTTP 409 without a promotion event when that guard refuses it. This also protects records whose stored session is empty. Repeated promotion in the same session remains as before; this guard does not change who may promote or its scope rules.

The added regressions cover a direct store collision, two racing store writers, a real cross-session promotion collision, and repeated same-session promotion. Five mutations were caught: removing the SQL session guard, silently ignoring a conflict, changing the HTTP status, writing an event before the refusal, and making repeated promotion insert-only. Each affected test failed under its targeted mutation and the restored suite passed 63 tests. A broader feedback, reference, recovery, browser, Pipeline and dispatch suite passed 217 tests, including the DOM probes. Refreshed accessibility, performance, cross-tab and historical release gate results were 120/120, 21/21, 2,200/2,200 and 37/37 plus 7/7. Backend safety again passed 309 tests and 16 isolation checks, with isolation unqualified and blocked.

## Same-session binding containment

The previously reproduced same-session collision was a promotion-derived preference ID overwriting an artifact-scoped record. The atomic upsert now also requires an existing ID's artifact, content digest and scope to match; that reproduction returns 409 without an event and preserves both records. This guard also prevents direct store updates from rebinding an ID to a different artifact, version or scope, even when two writers race. It retains the existing same-binding update and repeated-promotion behavior rather than changing promotion authority or approval rules.

Three mutations removing each new binding check were caught by direct store regressions; the artifact mutation was also caught by a concurrent-writer test, and the scope mutation by the integrated promotion reproduction. All restored feedback tests passed 68/68. The broader feedback, reference, recovery, browser, Pipeline and dispatch suite passed 222 tests. Refreshed accessibility and performance evidence passed 120/120 and 21/21; the cross-tab walk passed 2,200/2,200. Backend safety passed 309 tests and 16 isolation checks, with isolation unqualified and blocked.

**This is not complete feedback isolation or immutable history.** A same-binding update can still overwrite the existing record, including repeat promotions; concurrent confirm and withdrawal read-modify-write races remain. Checkpoint membership, current-file integrity, server authorization and recovery of records already overwritten remain outside this slice. Follow [issue 414](https://github.com/pankajtiwarics27/m5-agent-studio/issues/414). No confirmation, preference, acceptance or publishing authority is created by this fix.
