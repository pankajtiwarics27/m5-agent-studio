# Feedback capture identity collision

In a disposable application database, two different sessions submitted the same caller-supplied feedback ID. Before this change both capture requests returned 200: the second globally keyed upsert replaced the first record, and the original session could no longer list it. This was reproduced through the integrated routes, not just the storage class. The caller was already permitted to call those routes; this observation does not establish an authentication bypass.

Capture now uses an atomic SQLite insert with a uniqueness conflict refusal. A duplicate ID returns HTTP 409 without writing a feedback record or appending a capture event. The ID cannot be reused even after withdrawal; the retained record remains visible in its original session. The confirm, withdraw and promotion rules are not changed. Clients that intentionally supplied an existing ID to overwrite it must instead use a new ID; this is a deliberate compatibility change. Generated IDs already use random UUIDs, but the same collision refusal applies to them.

The focused route regression checks collisions in the same and a different session against an already confirmed record, then checks the withdrawn record cannot be resurrected into the other session. A simultaneous two-writer store regression requires exactly one insertion and one conflict. Reverting the capture route to upsert, replacing conflict refusal with an overwrite or a silent success, changing the 409 response, and appending a capture event before the refusal were each caught. The restored focused suite passed 59 tests. A broader feedback, reference, recovery and required-browser run passed 115 tests with two optional DOM probes skipped; those probes ran in a separate reference and recovery run with the dependency present, passing all 52 tests.

Refreshed accessibility and performance evidence passed 120/120 and 21/21; the cross-tab walk passed 2,200/2,200 checks over 48 captures. Backend safety passed 309 tests and 16 isolation checks, with isolation unqualified and blocked. The historical release gate passed 37/37 artifact checks and 7/7 phase gates; its old preservation approval remains unbound. These checks are not release approval.

**This is not a complete feedback isolation fix.** A separate integrated-route reproduction showed that promotion can still overwrite a different session's record when its derived preference ID collides with an existing ID. That path and repeated-promotion compatibility need separate review; neither was changed here. Existing confirm and withdrawal read-modify-write races, checkpoint membership, current-file integrity, server authorization and recovery of records already overwritten are also outside this slice. Follow [issue 414](https://github.com/pankajtiwarics27/m5-agent-studio/issues/414). No confirmation, preference, acceptance or publishing authority is created by this fix.
