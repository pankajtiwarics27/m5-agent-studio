# Recent work and the task handoff

Generated by `python3 scripts/uiux_recent_work_inventory.py` — **never hand-edit this page**.

Start shows the five most recent Harness sessions as buttons that open them where they live, painted through the same state table the Harness uses, and offers a composer that carries a task into the Harness without running it. Start reads the session list; it never creates, retitles or deletes a session.

## What Start reads

`GET /api/harness/sessions` returns the sessions already ordered by `updated_at DESC`, plus the default workspace and the recent directories the Harness uses. Start takes the first 5 and renders one row per session from `id`, `title`, `status`, `step_count`, `policy`, `workspace_dir`, `updated_at`. Nothing is copied into a second store: a row is a button that opens that session in the Harness, so the pane cannot drift from the sessions it shows.

8 of 8 statuses the server writes have a row in `harnessStatusBadge()`, the table every harness surface paints a run state with. A status without one would appear on Start as a bare lowercase word while the Harness showed a badge — two vocabularies for one state.

## The three states of the recent list

| State | What is shown |
|---|---|
| sessions exist | a bounded list of buttons, newest first, each with title, step count, policy, workspace folder tail and its state pill |
| none yet | the empty presentation: *No recent work yet*, why, what appears once one runs, and actions to start a session or open the Harness |
| unreadable | the error presentation: the cause, *nothing was changed; the task composer below still opens a task*, and Retry / Open Harness |

## The launcher is a handoff

`launchTaskFromStart()` writes the text into `#harnessPromptInput`, dispatches `input` so the composer's own listeners see it, focuses it and stops. It makes no request and calls nothing that runs: the workspace, the worktree decision and the execution policy are chosen in the Harness, and a run begun from a pane that cannot show them is a run begun with the wrong ones.

The note under the composer quotes the preflight's verdict — ready, or not ready with the next step named — and it is refreshed whenever the preflight is re-read, so it cannot say *ready* an hour after the lead stopped saying it. The same text is the composer's `aria-describedby`.

## Rules this artifact enforces

`--check` fails when the server writes a status with no tone or label, when the recent-work code reads any route other than the session list or issues a write method at all, when the list is rendered unbounded, when a row is not a `<button>` or is painted outside `setStatus()`/`harnessStatusBadge()`, when either presentation loses its cause or action, when the launcher makes a request or calls a run, when its note stops quoting the preflight, or when a state the renderer emits has no rule.

## Checks and limits

- the recent list is the Harness's own ordering (updated_at DESC), not a separate notion of recency invented here.
- the launcher hands a task over; whether it runs, and with which workspace and policy, is decided in the Harness.
- the browser walk creates and deletes its own sessions, so nothing in this artifact depends on demo state.
- a session's step count is what the server stored, not a count the pane recomputes from events.

The behaviour is measured by `node scripts/start_recent_walk.mjs`, which creates a session through the API the Harness uses, asserts the row and its state pill, opens it from the row, types a task and asserts that the composer received it while no session was created and nothing ran, then deletes what it created, exercises the empty presentation and finally refuses `/api/harness/sessions` to assert the error presentation and Retry.

## Regenerating

1. Change the pane in `static/index.html` or a status the server writes in `app.py`.
2. `python3 scripts/uiux_recent_work_inventory.py`.
3. `node scripts/start_recent_walk.mjs` against a running `scripts/demo_tour.py --serve`.
