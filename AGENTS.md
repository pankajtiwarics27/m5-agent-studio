# AGENTS.md — Working on this repository with an AI coding agent

This repository is designed so that an LLM agent (or a human) can clone it and
start productive work immediately, with no context beyond what is in the repo.
This file is the entry point: it tells you what the project is, where the work
plan lives, how to verify changes, and the rules every change must follow.

Read this file top to bottom before writing code.

Every session must also read and apply
[`docs/verification-efficiency.md`](docs/verification-efficiency.md): plan
risk-based verification, use the existing scoped selector during iteration,
profile avoidable delays, and report selected/reused/deferred evidence honestly.
Mandatory final, PR, security and release checks remain unchanged.

---

## 1. What this project is

M5 Agentic Studio is an open-source, **local-first** AI developer platform and
agent harness: a FastAPI backend (`app.py` + 22 contract modules), a vanilla
HTML/CSS/JS UI (`static/index.html`), and a generated standalone executable
(`studio.py`). It runs local models (oMLX/MLX, Ollama, llama.cpp) and cloud
providers behind one OpenAI-compatible gateway, with multi-agent workflows
(Harness, Council, Debate, GSD, SDLC), an MCP hub, and a SQLite/FTS5 context
engine. macOS (Apple Silicon) is the first target platform, but nothing may be
hard-coded to a chip, RAM size, model, or vendor.

## 2. Non-negotiable principles

Violating any of these is a rejected change, regardless of tests passing:

1. **Local-first privacy.** No startup-time, background, or implicit outbound
   requests. Cloud/network/billable actions require explicit user
   authorization (policy + consent), fail closed, and are tested.
2. **Hardware / model / provider independence.** No chip, RAM, model-name, or
   vendor hard-coding. Platform-specific capability must degrade explicitly.
3. **Secure defaults.** Execution, MCP stdio, and skill code are deny-by-default.
   Never weaken authentication, origin checks, rate limits, URL/IP pinning,
   approval scoping, sandboxing, audit, or secret handling without a focused
   security review plus positive and negative tests.
4. **Evidence over claims.** Never state that tests were run if they were not.
   Skipped or environment-blocked checks are reported as skipped.

Within the program you are working on, choose exactly one story that is both
owner-authorized and dependency-ready, respect phase order, and take one story
per branch and pull request. Dependency readiness alone is not authorization.
A UI/UX session never edits runtime/AP story tracking, and a runtime/AP session
never rewrites UI/UX tracking; backend behaviour a screen needs is an owning
runtime story or an open risk, never an API widening inside a UI pull request.

**Never self-certify a review gate.** Human verification of this repository is
performed **once, at the end, as final end-to-end testing** after all stories are
complete (maintainer decision 2026-10-29). AS-031 is therefore `completed`, not
`verified`. An agent may prepare evidence, remediate findings, and fix tooling,
but may not fill the reviewer severity, independence, or decision fields, may not
change the record to `signed`, and may not mark AS-031 `verified` on author-only
evidence. `verified` is reachable only through a signed `accepted` review.

## 4. Session start protocol

The roadmap's implementation playbook (in the JSON under
`implementation_playbook`) is the expected agent loop. In short:

1. Inspect the current repository state; do **not** assume the roadmap matches
   the code. Check the story's `status` and `status_evidence`, and grep for
   existing behavior before writing anything.
2. Summarize: current state, gap to the story's acceptance criteria, risks,
   dependencies, and a minimal implementation plan.
3. Implement the smallest maintainable change for **exactly one story**: typed
   contracts, backward compatibility or a documented migration, positive +
   negative + failure tests, docs, and regenerated artifacts.
4. Run the full verification sequence (below), report actual commands and
   results, then open a pull request.
5. Ask questions only when a blocking ambiguity exists; otherwise decide and
   document the decision in the pull request description.

For UI/UX coordination, `python3 scripts/uiux_coordination.py` reports local
readiness without network access; `--github` explicitly checks open PRs,
marked blocker issues and the current main commit. It is a read-only,
non-atomic advisory, not a claim or a replacement for [`M5_2_0_UIUX_AGENT_PROMPT.md`](M5_2_0_UIUX_AGENT_PROMPT.md).
See [`docs/uiux-2-0-coordination.md`](docs/uiux-2-0-coordination.md) for the
handoff, capture risks, and claim-window precautions.

## 5. Environment setup and verification

Python `>=3.11`. No model, provider, MCP, or cloud endpoint is needed for any
check. From a clean checkout:

```bash
python -m venv .venv && . .venv/bin/activate
python -m pip install -e '.[dev,supply-chain]'   # supply-chain = pip-audit for the release scan
python scripts/verify_baseline.py                # pinned Git ancestry (needs full history: git fetch --unshallow)
```

### 5.1 Local verification by risk

Match the commands to what the change can break instead of running the whole
checklist for every edit; the full suite is 10–13 minutes per run and running it
for a one-line doc edit costs more than it proves. CI is the merge gate and is
never relaxed by this table.

| Change touches | Minimum local run before pushing |
| --- | --- |
| Prose only (`README.md`, `docs/*.md`, `AGENTS.md`, `CONTRIBUTING.md`) | `python scripts/validate_docs.py`, plus any ADR check when `docs/adr/` changed |
| Roadmap/product JSON, or anything that generates a doc | the generators, then `git diff --exit-code` (see [§8](#8-generated-artifacts--regenerate-never-hand-edit)) |
| Screenshot manifest, `docs/media/` | `python scripts/validate_screenshots.py`, `python scripts/uiux_screenshot_review.py --check` |
| Release/governance records | `python scripts/validate_governance.py`, `python scripts/validate_security_signoff.py` |
| Supply chain, packaging, dependencies | `python scripts/release_supply_chain.py build` then `verify` |
| Runtime, storage, security, providers (`app.py`, `*.py` modules) | `ruff check .`, `mypy`, `python scripts/run_scoped_tests.py --base origin/main --head HEAD --worktree`, `python scripts/smoke_local.py` and `--standalone` |
| Frontend (`studio.py` is generated — edit its source), UI tests | `python scripts/check_frontend_syntax.py`, the affected `--area ui.*` selection, plus `scripts/build_studio.py` regeneration |
| Generated artifacts (`studio.py`, route matrix, subsystem inventory) | regenerate all three and `git diff --exit-code` |
| Test infrastructure, `tests/test_scopes.json`, workflow or CI config | the full suite (`python -m pytest -q`): the selector cannot reason about its own change |

Anything not listed, any change spanning several rows, and any change whose
blast radius you cannot state in one sentence: run the full suite. Before
requesting review of an implementation PR, ensure it has left draft so the full
merge gate runs. Documentation-only PRs use the focused documentation and
tracking-ledger checks. Before merging or claiming an implementation story is
done, the required gate for that change class must pass at the current head;
CI remains authoritative.

### 5.2 Scoped test selection

The selector maps changed paths to feature areas through
`tests/test_scopes.json`:

```bash
python scripts/run_scoped_tests.py --base origin/main --head HEAD --worktree
python scripts/run_scoped_tests.py --area ui.compare      # explicit feature run
python scripts/run_scoped_tests.py --check-map            # every module is categorized
```

Unknown, shared, or high-risk paths fall back to the full suite inside the
selector itself.

### 5.3 What CI runs, and when

One run per event lane; the pull request owns the merge gate and is never
cancelled by a cheaper push run:

- **Draft pull request**: mapped implementation changes run the scoped Python
  selection on Python 3.11, 3.12 and 3.13. Known documentation-only edits and
  the AP tracking ledger run focused documentation/governance/ledger checks.
  High-risk, unmapped, test-infrastructure, workflow and runtime product-input
  changes fail closed to the full gate. Browser safety is deferred until the
  full gate.
- **Ready-for-review pull request**: implementation changes run the full Python
  suite on Python 3.11, 3.12 and 3.13 plus browser safety. Known documentation-
  only edits retain the focused gate. This is the authoritative merge-gate run;
  a newer push supersedes an in-flight run for the same pull request. Converting
  a draft to ready-for-review triggers the full gate.
- **Push without an open pull request** (feature branch): scoped selection.
  When a branch already has an open pull request, the push run is a cheap
  placeholder because that PR's selected gate owns coverage. `main` pushes
  always run in full.
- **Push to `main`**, **nightly schedule** (`17 7 * * *`), **manual dispatch**:
  full suite plus browser safety, never cancelled by concurrency.
- Every run streams pytest output and `--durations` while it executes, and
  prints the slowest tests and a `::notice` summary with the elapsed seconds.

A pull request is mergeable only when the stable Python (`test`) and browser
safety check statuses are green. Those aggregate checks must confirm the
selected gate succeeded: focused docs tests for the explicit documentation
allowlist, mapped scoped Python tests for draft edits, or the full Python and
browser gates for ready implementation and any uncertain/high-risk change.

### 5.4 Full gate

The complete set CI enforces on a merge-gate run. Run it locally when the risk
table points here, and reproduce any red CI leg with these exact commands:

```bash

python scripts/check_frontend_syntax.py                 # needs Node.js
python scripts/run_scoped_tests.py --check-map           # every module is categorized
python -m pytest -q                                     # full suite on 3.11, 3.12, 3.13 in CI

python scripts/smoke_local.py && python scripts/smoke_local.py --standalone
```

### 5.5 Measure the suite before changing how it runs

Do not make CI faster by guessing. Profile first, then change the trigger or the
step that the profile names:

- `python -m pytest -q --durations=30 --durations-min=1.0` is the local profile;
  CI prints the same list (`--durations=15`) inside the run log, plus a
  `::notice` line with the step's elapsed seconds.
- The local and CI profiles are not the same profile: CI installs no
  ImageMagick, so the pixel pass over `docs/media/` costs minutes locally and
  nothing there. Optimise the machine you measured.
- Sharding, `xdist`, or dropping a leg changes coverage. Justify it from the
  measured CI-side numbers, not from local wall clock.
- A run is never restarted to look faster. Report the run id, the unfinished
  job, and the queue-versus-execute split instead.

Banked results, the current baseline, and the single owner of the next
critical-path experiment are recorded in
[`docs/verification-critical-path-plan.md`](docs/verification-critical-path-plan.md).
Do not start a competing CI optimisation while an owner is named there.

## 6. Branch, commit, and merge rules

- **Branches:** one story per branch, named `as-XXX-short-slug` (e.g.
  `as-030-history-retention`). Dependabot and CI-platform branches keep their
  own conventions.
- **Every commit must be documented** — a future reader must understand it
  without diffing the tree:
  - Subject: 8–100 chars, imperative, no trailing period. Prefer
    `AS-XXX: <what changed>` for story work, or `type: <what changed>`
    (`feat|fix|docs|refactor|test|chore|ci`) otherwise.
  - Body: blank line after the subject, then what changed, why, and the
    evidence (tests added, commands run, tradeoffs, blockers).
  - `scripts/check_commit_messages.py --base origin/main` enforces this on new
    commits; the CI run will fail otherwise. Example:

    ```
    AS-030: Add history retention and export controls

    Adds opt-in retention windows and authenticated export for local
    conversation history, per AS-030 acceptance criteria. ...
    Evidence: pytest -q (N passed), smoke_local.py x2, artifacts regenerated.
    ```
- **Merges:** rebase-merge (linear history) for AS-program branches. Branches are **deleted
  automatically on merge** (repository setting `delete_branch_on_merge`);
  do not reuse or re-push a merged branch name. **M5 2.0 multi-agent story
  PRs are a scoped exception:** merge them with `gh pr merge <number> --merge`
  (merge commit) so long-lived session branches stay consistent with `main`
  and sequential PRs do not replay duplicate commits; see
  [`M5_2_0_AGENT_PROMPT.md`](M5_2_0_AGENT_PROMPT.md) for the full
  multi-agent claim/review/merge protocol.

## 7. Landing a story: the status contract

When a pull request completes a story (or advances its verification):

1. Update the story's `status`, `status_evidence`, and `status_updated` in
   `product/Adaptive_Runtime_Product_Roadmap_v2.json`, plus
   `status_tracking.last_updated`. Use the documented vocabulary:
   - `verified` — implemented, merged CI green, dedicated automated tests on main;
   - `completed` — implemented and merged CI green, with a named validation
     aspect still outstanding (state exactly what and why);
   - `in_progress` — partially satisfied (state what exists and what remains);
   - `planned` — untouched.
2. Regenerate the dashboard (`python scripts/generate_roadmap_status.py`) and
   commit both files in the same pull request — CI fails if they drift.
3. Update any docs the story owns (`docs/*.md`, `README.md`,
   `IMPLEMENTATION_STATUS.md`) in the same change.

Status changes without the underlying implementation or evidence in the same
PR are rejected.

## 9. Hard guardrails

- Never modify or reword `BASELINE_COMMIT`, and never break its ancestry.
- Never add a runtime dependency, public API, or config surface silently —
  document it, test it, and record a decision in `docs/adr/` when the choice is
  long-lived (the roadmap's `architecture_decision_records` list shows the
  planned ADR series).
- Tests must never contact live model, cloud, MCP, or network endpoints; use
  fakes, temporary paths, and disposable loopback servers. The container
  runtime test is opt-in and stays skipped in normal CI.
- `GET /healthz` is the only unauthenticated route; everything under `/api/*`
  and `/v1/*` requires the bearer token. Keep it that way.
- Preserve the runtime invariants in [`README.md` § Critical invariants](README.md#critical-invariants)
  (oMLX unload semantics, MCP `Accept` headers, tool-call dialects, secret-read
  guards, and the rest).
- Keep generated artifacts, `.harnesses/`, databases, tokens, and credentials
  out of commits (`.gitignore` covers them; keep it that way).
